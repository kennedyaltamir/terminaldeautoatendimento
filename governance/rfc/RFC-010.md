
# RFC-010: Enum Lifecycle & Deprecation Policy
**Status:** ACTIVE
**Version:** 1.0
**Domain:** BACKEND_ARCHITECTURE
**Date:** 2026-01-11

## 1. Objetivo
Estabelecer um rito formal para a evolução de tipos enumerados (Enums) no MesaFlow, garantindo que a introdução de novos estados ou a remoção de antigos não cause falhas em clientes (Mobile/Frontend) com versões de cache divergentes.

## 2. Estados do Ciclo de Vida
Todo membro de um Enum deve pertencer a um dos seguintes estados:

| Estado | Descrição | Ação no Backend | Ação no Frontend/Mobile |
| :--- | :--- | :--- | :--- |
| `ACTIVE` | Valor em uso pleno. | Suporte total (R/W). | Renderização normal. |
| `DEPRECATED` | Valor em fase de descontinuação. | Aceita leitura, mas evita escrita. | Exibe aviso (se admin) ou ignora. |
| `RETIRED` | Valor removido da lógica. | Lança erro se recebido. | Removido do código. |

## 3. Regras de Transição (Breaking Changes)
1.  **Adição:** Novos valores podem ser adicionados como `ACTIVE`. Devem ser retrocompatíveis com a lógica de fallback do Frontend.
2.  **Depreciação:** Um valor deve permanecer como `DEPRECATED` por pelo menos um ciclo de release (Quarter) antes de ser `RETIRED`.
3.  **Remoção:** Valores `RETIRED` só podem ser removidos fisicamente do código após auditoria de banco de dados confirmando zero ocorrências (TASK-GOV-11).

## 4. Matriz de Compatibilidade
O Backend deve sempre fornecer um `fallback_value` em Schemas Pydantic para Enums críticos, permitindo que versões antigas do App Mobile processem estados desconhecidos sem crashar.
