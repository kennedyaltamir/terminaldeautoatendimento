# ADR-000A: MesaFlow OS — Filosofia Operacional e Eliminação de Latência

**Status:** ACEITA
**Decisores:** MesaFlow Kernel Board
**Foco:** Visão Executiva e Estratégica

## 1. O Problema: O Custo da Fila e da Incerteza
Sistemas tradicionais de gestão falham porque tratam a operação como um registro passivo de eventos passados. Em ambientes de alta pressão, a **Fila** não é apenas uma linha de espera; é um **vazamento de margem operacional**, gerando:
* **Abandono de Compra:** Fricção no checkout reduz conversão.
* **Inércia Humana:** Funcionários sem direção clara geram "bolhas" de atraso.
* **Estresse Sistêmico:** Decisões sob pressão sem dados geram erros e churn.

## 2. A Solução: Orquestração Simétrica
O MesaFlow OS não é um software de pedidos. É um **Sistema de Eliminação de Latência**. Ele transforma a operação em um fluxo contínuo e sincronizado entre:
1. **Intenção (Cliente):** Transformada em dado instantâneo.
2. **Capacidade (Produção/Serviço):** Orquestrada por demanda real.
3. **Logística (Distribuição):** Integrada ao tempo de preparo.

## 3. Pilares da Soberania Operacional
* **Fluxos Determinísticos:** A tecnologia guia o humano para a próxima tarefa de maior valor.
* **Throughput como Prioridade:** O sucesso é medido pela vazão total do sistema, não por tarefas isoladas.
* **Visibilidade Prescritiva:** O dashboard não apenas mostra o erro, ele sugere a correção (ex: mover staff entre setores).

## 4. Business Equation (Equação de Valor)
`↑ Throughput Operacional (Sem aumento de Headcount) = ↑ Margem Líquida + ↓ Time-to-Revenue`

---
*Este documento define a alma do MesaFlow OS e orienta todas as decisões técnicas subsequentes.*

# ADR-000B: Anti-Goals e Não-Objetivos (Escopo Estratégico)

**Status:** ACEITA  
**Objetivo:** Manter o foco absoluto na orquestração de fluxo.

## 1. O que NÃO somos
Para garantir a soberania no combate às filas, o MesaFlow OS recusa-se a ser:
* **ERP Contábil/Fiscal Generalista:** Não substituímos sistemas de contabilidade complexos. Integramos com eles via API.
* **CRM de Marketing de Massa:** Não somos uma ferramenta de envio de spam. Focamos em retenção via fidelidade tática (Cashback).
* **Gestor de Folha de Pagamento:** Monitoramos a produtividade do funcionário, mas não processamos tributos trabalhistas.

## 2. Motivação
A tentativa de resolver problemas periféricos gera "Feature Creep" e degrada a performance do motor de decisão central (The Kernel).

# ADR-001: Adoção de FastAPI como Backend Framework

**Status:** ACEITA (Soberana)
**Data:** Outubro de 2025 (Revisada em Fevereiro de 2026)
**Versão:** 2.0
**Decisores:** MesaFlow OS Kernel, Architecture Lead

## 1. Contexto
O MesaFlow OS opera como um Sistema Operacional para Food Service, exigindo:
1. **Baixa Latência:** Respostas de API < 100ms para PDV e KDS.
2. **Real-time:** Conexões persistentes via WebSockets para sincronia de pedidos.
3. **Segurança Financeira:** Validação rigorosa de payloads de pagamento (Pix/Stripe) para evitar *Data Corruption*.
4. **Prontidão para IA:** Facilidade de integração com bibliotecas de Data Science (Scikit-learn, Pandas) para o motor de predição de demanda.

## 2. Decisão
Adotamos **FastAPI (Python 3.11+)** com **Pydantic v2** como o núcleo do Kernel Backend.

## 3. Justificativa Técnica
* **Performance Brutal:** Baseado em Starlette (ASGI), o FastAPI oferece performance comparável ao Go e Node.js em cenários de alta concorrência.
* **Validação por Contrato:** O uso exaustivo do Pydantic garante que nenhum dado malformado entre no banco de dados Neon, servindo como primeira barreira de segurança.
* **Autodocumentação (OpenAPI):** Redução de 40% no tempo de integração entre Frontend e Backend através da geração automática do Swagger.
* **Ecossistema IA:** A escolha do Python nos permite rodar o `AiPredictionService` nativamente no mesmo processo do Kernel, reduzindo latência de rede entre microsserviços.

## 4. Alternativas Consideradas

| Alternativa | Veredito | Motivo do Descarte |
| :--- | :--- | :--- |
| **Django** | REJEITADO | Síncrono por design em muitas camadas, overhead excessivo de ORM para o que o MesaFlow exige. |
| **Node.js (NestJS)** | REJEITADO | Embora rápido, a fragmentação do ecossistema de criptografia e a dificuldade de lidar com Python para IA criariam um débito técnico futuro. |
| **Go (Gin/Echo)** | REJEITADO | Alta performance, mas curva de aprendizado e velocidade de iteração (Time-to-Market) inferiores ao Python para o MVP. |

## 5. Consequências

### ✅ Positivas
* **Concorrência:** Capacidade nativa de lidar com milhares de entregadores conectados simultaneamente.
* **Tipagem Estrita:** Uso de *Type Hints* do Python 3 permite detecção de erros em tempo de desenvolvimento.
* **Extensibilidade:** Integração simplificada com Redis Pub/Sub (ADR-007).

### ⚠️ Negativas
* **Gestão de Dependências:** Exige disciplina rigorosa com `requirements.txt` e ambientes virtuais (.venv).
* **Desenho de Segurança:** Ao contrário do Django, o FastAPI exige que a arquitetura de segurança (JWT, OAuth2) seja desenhada e implementada manualmente (implementado com sucesso na ADR-005).

## 6. Compliance
Esta decisão cumpre os requisitos de Soberania Técnica e Escalabilidade Horizontal definidos para o MesaFlow OS.

# ADR-002: Uso de Neon.tech (PostgreSQL Serverless)

**Status:** ACEITA (Soberana)
**Data:** Outubro de 2025 (Revisada em Fevereiro de 2026)
**Versão:** 2.0
**Decisores:** MesaFlow OS Kernel, Infrastructure Council

## 1. Contexto
O MesaFlow OS exige uma camada de persistência que suporte:
1. **Isolamento Lógico (Multi-tenancy):** Implementação nativa de Row-Level Security (RLS) para garantir que os dados da "Hamburgueria A" sejam invisíveis para a "Pizzaria B".
2. **Elasticidade Extrema:** Capacidade de lidar com picos de tráfego (ex: horário de almoço ou grandes eventos) sem intervenção manual de escala.
3. **Resiliência de Dados:** Backups granulares e ritos de recuperação instantânea em caso de corrupção lógica.
4. **Forense e Debugging:** Necessidade de testar correções em ambientes que espelham exatamente a produção (Volume e Schema).

## 2. Decisão
Adotamos o **Neon.tech (PostgreSQL Serverless)** como motor de persistência primário.

## 3. Justificativa Técnica
* **Arquitetura de Separação (Compute/Storage):** Ao contrário do RDS tradicional, o Neon separa processamento de armazenamento. Isso permite o rito de *Scale-to-Zero* (economia em desenvolvimento) e *Instant Scaling* (performance em produção).
* **Soberania via RLS:** O Neon oferece suporte total às políticas de segurança do PostgreSQL (implementadas via migrations Alembic), sendo o executor final da nossa política de isolamento de tenants.
* **Database Branching (Forense):** Capacidade única de criar um "clone" instantâneo do banco de dados de produção para um ambiente de homologação. Essencial para o nosso protocolo de **Autópsia de Bugs** sem afetar usuários reais.
* **Sincronia com FastAPI:** O uso de *Connection Pooling* nativo (via PgBouncer/Endpoint de transação) resolve o problema de limite de conexões comum em arquiteturas serverless assíncronas.

## 4. Alternativas Consideradas

| Alternativa | Veredito | Motivo do Descarte |
| :--- | :--- | :--- |
| **AWS RDS** | REJEITADO | Custo fixo elevado e lentidão no scaling vertical. Exigiria gestão manual de VPCs e manutenção de patches. |
| **Supabase** | REJEITADO | Oferece muitos recursos de aplicação (Auth, Edge Functions) que o MesaFlow já possui nativamente no Kernel, gerando redundância e dependência tecnológica excessiva. |
| **Postgres Nativo (Docker)** | REJEITADO | Inviável para produção em larga escala sem uma equipe dedicada de DBA para gerenciar backups, replicação e disponibilidade. |

## 5. Consequências

### ✅ Positivas
* **Time-to-Production:** Zero tempo gasto em provisionamento de hardware.
* **Integridade:** Uso de *Point-in-Time Recovery* (PITR) permite retornar o sistema a qualquer segundo anterior a uma falha crítica.
* **Economia:** O faturamento é baseado apenas no consumo real de processamento.

### ⚠️ Negativas
* **Latência de "Cold Start":** No plano gratuito, a primeira requisição após inatividade pode demorar (>2s). *Mitigação:* Uso do plano Pro/Autoscale para produção.
* **Dependência de Infra Externo:** Embora o dado seja Postgres padrão, a orquestração de escala e branching é proprietária do Neon.

## 6. Compliance
Esta decisão está em conformidade com as diretrizes de LGPD e segurança de dados, utilizando criptografia em repouso e isolamento de tenant via RLS validado na ADR-005.

# ADR-003: Render.com como Plataforma de Runtime

**Status:** ACEITA (Soberana)
**Data:** Novembro de 2025 (Revisada em Fevereiro de 2026)
**Versão:** 2.0
**Decisores:** MesaFlow OS Kernel, DevOps Council

## 1. Contexto
O MesaFlow OS exige um ambiente de execução que suporte:
1. **Conexões Persistentes (WebSockets):** O monitor de cozinha (KDS) e o cockpit do motorista dependem de túneis de baixa latência que não podem ser interrompidos por timeouts de arquiteturas "Serverless" puras.
2. **Background Workers:** Necessidade de rodar processos assíncronos contínuos para o `IfoodService` (polling/webhooks) e processamento de `FinancialLedger`.
3. **GitOps Nativo:** Fluxo de deploy automatizado via `main` branch com ritos de rollback imediato.
4. **Comunicação Privada:** Isolamento de rede para que o Kernel API e o Redis não fiquem expostos à internet pública, comunicando-se apenas via rede interna.

## 2. Decisão
Adotamos **Render.com** como o ecossistema de runtime para o Backend (Web Service), Workers e orquestração de infraestrutura.

## 3. Justificativa Técnica
* **Suporte Nativo a WebSockets:** Diferente do Vercel ou AWS Lambda, o Render permite conexões HTTP persistentes sem limite de execução (Timeouts de 30s-60s), o que é vital para a sincronia do salão e produção.
* **Orquestração de Instâncias (Scale-Out):** Facilidade em escalar o número de instâncias do Kernel Backend em resposta à carga detectada pelo nosso motor de monitoramento.
* **Blueprints (Infrastructure as Code):** Uso de `render.yaml` para garantir que o ambiente de Produção seja um espelho exato do ambiente de Staging, eliminando o erro "funciona na minha máquina".
* **Auto-Healing:** O Render monitora o rito de boot e, caso o Kernel API falhe (ex: erro de configuração de ENV ou porta), ele impede o tráfego de chegar à nova instância, garantindo zero tempo de inatividade (*Zero Downtime Deploys*).

## 4. Alternativas Consideradas

| Alternativa | Veredito | Motivo do Descarte |
| :--- | :--- | :--- |
| **AWS ECS (Fargate)** | REJEITADO | Complexidade excessiva de IAM e VPC para a fase atual. Alto tempo gasto em "encanamento de infra" em vez de lógica de negócio. |
| **Heroku** | REJEITADO | Preços proibitivos para instâncias que não entram em sleep. Limitações de rede privada no plano padrão. |
| **Vercel (Backend)** | REJEITADO | Inadequado para WebSockets e tarefas de longa duração. Inviabiliza o motor de integração com iFood e o Sentinel Mode. |

## 5. Consequências

### ✅ Positivas
* **Segurança L7:** SSL (TLS 1.3) gerenciado e renovado automaticamente.
* **Forense:** Acesso centralizado a logs de runtime e histórico de deploys.
* **Rede Interna:** Latência mínima na comunicação entre API e Redis.

### ⚠️ Negativas
* **Build Time:** O processo de build de containers Docker pode demorar de 3 a 5 minutos, o que exige um fluxo de Staging/QA antes do merge na `main`.
* **Lock-in Parcial:** Dependência das funcionalidades de rede interna do Render.

## 6. Compliance
Esta decisão está alinhada com as normas ISO 27001 para gestão de ativos e disponibilidade de serviço (SLA de 99.9%).

# ADR-004: Estratégia de Dual Health Endpoint

**Status:** ACEITA (Soberana)
**Data:** Janeiro de 2026 (Revisada em Fevereiro de 2026)
**Versão:** 2.0
**Decisores:** MesaFlow OS Kernel, SRE Council

## 1. Contexto
A resiliência operacional do MesaFlow OS depende da capacidade de ferramentas externas e internas (Load Balancers do Render, UptimeRobot, Prometheus) validarem a vitalidade do Kernel. 
Dificuldades identificadas:
1. **Conveção vs. Estrutura:** Ferramentas de infraestrutura PaaS/IaaS buscam `/health` na raiz por padrão.
2. **Isolamento de Roteamento:** Erros em roteadores específicos da API (ex: `/api/v1/auth`) poderiam, em teoria, "cegar" o monitoramento se este estivesse aninhado no mesmo prefixo.
3. **SLA Transparency:** Necessidade de expor o estado de saúde para o *Trust Center* público sem expor detalhes sensíveis da infraestrutura.

## 2. Decisão
Implementar **Dual Path Binding** para a lógica de monitoramento. Um único controlador de saúde (Sentinel Probe) é mapeado simultaneamente para:
*   `/health` (Escopo de Infraestrutura / Root)
*   `/api/health` (Escopo de Integração / Namespace API)

## 3. Justificativa Técnica
* **Decorator Stacking:** O FastAPI permite empilhar rotas (`@app.get("/health")` + `@router.get("/health")`) sobre a mesma função assíncrona, garantindo que a lógica de verificação (DB Ping, Redis Check, Memória) seja idêntica em ambos os caminhos.
* **Compatibilidade "Out-of-the-box":** Elimina a necessidade de configurações personalizadas em Load Balancers, reduzindo a chance de erro humano no provisionamento da infraestrutura.
* **Resiliência do Kernel:** Se o roteador principal da API falhar ao carregar devido a uma dependência quebrada, o endpoint de saúde da raiz (`/health`) ainda pode responder, permitindo que o Sentinel identifique o erro exato (ex: 500 ou 503) em vez de um 404 genérico.
* **Sovereign Transparency:** Facilita a alimentação da página de status pública (`/trust/status`), servindo como base para o cálculo automático de SLA.

## 4. Alternativas Consideradas

| Alternativa | Veredito | Motivo do Descarte |
| :--- | :--- | :--- |
| **307 Temporary Redirect** | REJEITADO | Muitos agentes de monitoramento simplistas não seguem redirecionamentos e marcariam o sistema como "Down". |
| **Path Aliasing via Nginx** | REJEITADO | Adiciona complexidade fora do controle do Kernel. O MesaFlow deve ser autossuficiente e "cloud-agnostic". |
| **Apenas `/api/health`** | REJEITADO | Gera falsos positivos em ferramentas que não permitem customização de path de healthcheck. |

## 5. Consequências

### ✅ Positivas
* **Monitoramento Robusto:** Suporte universal a qualquer ferramenta de observabilidade do mercado.
* **Zero Overhead:** A lógica é centralizada e processada uma única vez; o mapeamento duplo é apenas uma entrada na tabela de rotas do Kernel.
* **Documentação Limpa:** Ambas as rotas são incluídas no OpenAPI, facilitando o trabalho da equipe de DevOps.

### ⚠️ Negativas
* **Exposição Visual:** Duas entradas no Swagger para a mesma função (mitigado pelo uso de Tags e agrupação de "Infrastructure").

## 6. Compliance
Esta estratégia garante a rastreabilidade contínua da disponibilidade do sistema, conforme exigido pelos ritos de Governança Cognitiva L7.

# ADR-005: Hardening de Segurança (RLS, Bcrypt Nativo e Headers)

**Status:** ACEITA (Soberana)
**Data:** Janeiro de 2026 (Revisada em Fevereiro de 2026)
**Versão:** 2.1 (Gold Master Edition)
**Decisores:** MesaFlow OS Kernel, Security Architecture

## 1. Contexto
O MesaFlow OS é um ambiente multi-tenant que processa dados financeiros, fiscais e operacionais. 
**Threat Model (Modelo de Ameaça):**
1. **Comprometimento da Camada de Aplicação:** Se um invasor ganhar controle da API, ele não deve conseguir ler dados de outros restaurantes.
2. **Erro Humano (Desenvolvimento):** Desenvolvedores podem esquecer cláusulas `.filter(company_id=...)` em novas rotas.
3. **Engenharia Social / Brute Force:** Tentativas de acesso indevido via senhas fracas ou payloads malformados.

## 2. Decisão
Implementar o **Protocolo de Defesa em Profundidade (L7)**:
1. **Isolamento de Persistência (RLS):** Row-Level Security nativo no PostgreSQL acionado via variável de sessão `app.current_company_id`.
2. **Soberania de Criptografia:** Abandono de middlewares obsoletos (passlib) em favor do driver nativo `bcrypt` com rito de truncamento mandatório (72 bytes).
3. **Blindagem de Transporte:** Injeção de Headers de Segurança (HSTS, CSP, X-Frame-Options) via middleware global.
4. **Sessão Forense:** Uso de JTIs únicos e rotação de Refresh Tokens para impedir *Replay Attacks*.

## 3. Justificativa Técnica
* **RLS como Invariante:** Ao definir a política no banco (`USING (company_id = current_setting('app.current_company_id'))`), o próprio motor do Postgres bloqueia a leitura. Se o código da API tentar ler "tudo", o banco retornará apenas o que pertence ao tenant logado. É a segurança que independe do código.
* **Bcrypt Nativo (Rito de Estabilidade):** Identificamos que abstrações de terceiros falham em ambientes modernos. O uso direto de `bcrypt.hashpw` garante que senhas < 72 bytes não causem *Kernel Panics* e permaneçam seguras.
* **Headers de Segurança:** Protegem contra ataques de *Cross-Site Scripting (XSS)* e *Clickjacking*, garantindo que a interface do MesaFlow seja renderizada apenas em contextos confiáveis.
* **Auditoria Estruturada:** Todo evento de segurança (Login, Falha de Auth, Reset de Senha) é logado em formato JSON para ingestão imediata por sistemas de SIEM (como o Sentry).

## 4. Alternativas Consideradas

| Alternativa | Veredito | Motivo do Descarte |
| :--- | :--- | :--- |
| **Filtros via ORM** | REJEITADO | Extremamente propenso a erro humano. Um único `query(Order).all()` sem filtro causaria um vazamento massivo de privacidade. |
| **Bancos Separados** | REJEITADO | Custo de manutenção de infraestrutura cresce exponencialmente com o número de clientes. Inviável para modelo SaaS de alta escala. |

## 5. Consequências

### ✅ Positivas
* **Imunidade IDOR:** Ataques de troca de ID de recurso (Insecure Direct Object Reference) são neutralizados no nível do hardware/banco.
* **Conformidade LGPD:** Atende nativamente aos requisitos de "Privacidade por Design".
* **Confiança Operacional:** Erros de desenvolvimento que cruzariam dados são capturados pelo banco antes de chegarem à tela do cliente.

### ⚠️ Negativas
* **Overhead de Sessão:** Toda conexão de banco exige o rito `SET LOCAL app.current_company_id`.
* **Complexidade Analítica:** Relatórios globais (BI da plataforma) exigem bypass explícito da política de segurança (bypassRLS).

## 6. Compliance
Esta ADR serve como documento oficial para auditorias SOC2 e Due Diligence de clientes Enterprise.

# ADR-007: Orquestração Real-time e Persistência de Eventos

**Status:** ACEITA (Hardened)
**Versão:** 2.0 (Migration Path to Redis Streams)

## 1. Contexto
A propagação de eventos no MesaFlow OS (KDS, Logística) é crítica. O modelo anterior (Pub/Sub puro) é volátil e não garante entrega em caso de instabilidade de rede ou reinício do servidor.

## 2. Decisão
Utilizar o Redis como backplane de mensagens, mas com diferenciação de criticidade:
1. **Eventos Efêmeros (ex: digitação, telemetria intermediária):** Pub/Sub padrão (Fire-and-forget).

* **Garantia de Entrega:** Uso de `XACK` para confirmar processamento. Mensagens não confirmadas são recuperadas via rito de auditoria periódico.
* **Failure Mode:** Se o Redis falhar, o Kernel entra em modo "Fail-Open Local", degradando para polling de banco de dados a cada 15s até a restauração do backplane.
* **Escalabilidade:** Testado para suportar até 5.000 conexões simultâneas por cluster Redis standard.

## 4. Business Equation
`Confiabilidade de Mensagem = 99.9% de Pedidos Sincronizados em < 200ms`

# ADR-008: Lógica de Negócio via Máquinas de Estado (FSM)

**Status:** ACEITA
**Data:** Fevereiro de 2026
**Versão:** 1.0
**Decisores:** MesaFlow OS Kernel, Logic Systems Designer

## 1. Contexto
Sistemas de Food Service e Logística lidam com fluxos de trabalho lineares mas críticos. Um pedido não pode ser "Entregue" se não foi "Aceito", e um motorista não pode estar "Em Rota" se o seu turno está "Offline". O uso de variáveis booleanas espalhadas (`isLoading`, `isAccepted`) gera o chamado "Estado Impossível" e bugs de UI difíceis de rastrear.

## 2. Decisão
Implementar toda a lógica de transição crítica (KDS, Cockpit do Motorista, Pagamentos) utilizando **Máquinas de Estado Finitas (FSM)** determinísticas.

## 3. Justificativa Técnica
* **Determinismo:** O sistema possui estados mutuamente exclusivos (ex: IDLE, ASSIGNED, EN_ROUTE). É impossível para o código forçar uma transição ilegal.
* **Previsibilidade:** O comportamento do sistema é definido por um mapa de transições claro, facilitando a escrita de testes automatizados (Playwright) e auditorias forenses.
* **Isolamento de Erro:** Se uma transição falha, o sistema sabe exatamente de onde veio e para onde deve retornar (Rollback de Estado), evitando que a interface fique travada.
* **Sincronia Offline-First:** A FSM permite enfileirar eventos quando a rede cai e processá-los na ordem lógica correta quando a conexão retorna (Protocolo Replay).

## 4. Implementação no MesaFlow
1. **DriverMachine:** Controla o ciclo de vida do entregador (Shift -> Mission -> POD).
2. **KdsReducer:** Controla a fila de produção (Pending -> Preparing -> Ready -> Bump).
3. **TableFSM:** Gerencia a ocupação física do salão e ritos de PIN.

## 5. Alternativas Consideradas

| Alternativa | Veredito | Motivo do Descarte |
| :--- | :--- | :--- |
| **Nested If/Else Logic** | REJEITADO | Resulta em código "espaguete" e estados inconsistentes em alta concorrência. |
| **Redux Saga / Thunk** | REJEITADO | Overhead excessivo de boilerplate para lógica que é inerentemente sequencial e dependente do domínio. |

## 6. Consequências

### ✅ Positivas
* **Bugs Zero em Transição:** Eliminação total de erros onde um pedido "some" ou pula etapas.
* **Telemetria Rica:** Cada transição de estado gera um log auditável no `financial_ledger` ou `audit_logs`.
* **UX Tática:** A interface reage instantaneamente ao estado da máquina (ex: Theater Mode).

### ⚠️ Negativas
* **Rigidez:** Mudanças no fluxo de negócio exigem a atualização formal do mapa de transições da máquina.
* **Curva de Design:** Exige que o desenvolvedor pense no fluxo completo antes de escrever o código da tela.

---
*Este rito de lógica garante a Soberania Operacional do MesaFlow OS.*

* **Exploração do Gargalo:** O sistema identifica o nó mais lento (ex: Cozinha) e dita o ritmo de entrada (Drum-Buffer-Rope), evitando o transbordamento operacional de outros setores.

## 4. Impacto
Permite a implementação do **Digital Twin Operacional**, onde o gestor pode simular cenários: "E se eu adicionar um operador neste nó?"

# ADR-022: Economic & Human Guardrails (Proteção de Ativos)

**Status:** ACEITA  

## 1. Contexto
A otimização matemática agressiva do Throughput pode levar ao esgotamento (burnout) da equipe e queda na qualidade do produto final.

## 2. Decisão
Implementar **Limitadores de Saturação**:
* **Max Operator Load:** O sistema impede o envio de novos pedidos para um nó de produção se o tempo de preparo estimado exceder 200% do SLA padrão.
* **Flow Throttling:** Redução automática da velocidade de entrada (Kiosk/QR) para preservar a integridade da entrega.
* **Fair Distribution:** Algoritmo de distribuição de tarefas que evita sobrecarga repetitiva em um único colaborador.

## 3. Business Equation
`Produção Sustentável = Throughput Máximo - Risco de Turnover`

# ADR-025: Limites de Responsabilidade e Decisão Automatizada

**Status:** ACEITA
**Tags:** Legal, Ethics, Compliance

## 1. Contexto
O sistema sugere alocação de equipe e priorização de filas. Erros nessas sugestões podem ter consequências financeiras ou trabalhistas.

## 2. Decisão
O MesaFlow OS opera sob o princípio de **Copiloto Operacional**:
* **Automação de Fluxo:** O sistema automatiza a *comunicação*, mas a *decisão final de execução* é do operador humano.
* **Isenção Algorítmica:** Recomendações de redistribuição de staff (ADR-013) são classificadas como "Sugestões de Otimização", não ordens imperativas.
* **Human-in-the-loop:** Ações críticas (Cancelamentos, Estornos, Mudança de Preço) exigem interação humana explícita.

## 3. Compliance
Garantir que os Termos de Uso (ToS) reflitam que o software é uma ferramenta de suporte à decisão, transferindo a responsabilidade operacional para o gestor da unidade.

# ADR-026: Estratégia de Dados para BI de Alta Performance

**Status:** ACEITA

## 1. Contexto
O Row-Level Security (RLS) impõe um overhead de performance que inviabiliza consultas analíticas complexas (BI) em tempo real para redes com centenas de unidades.

## 2. Decisão
Adotar o padrão **CQRS (Command Query Responsibility Segregation)** para dados de BI:
1. **Write Model (Transactional):** Neon PostgreSQL com RLS ativo (ADR-002, 005).
2. **Read Model (Analytics):** Replicação assíncrona (CDC) para um Data Warehouse (ex: ClickHouse ou BigQuery) sem as travas de RLS.

## 3. Justificativa
Garantir que relatórios executivos rodem em < 1s sem afetar a performance do banco de dados operacional das lojas.

# ADR-999: Fosso Competitivo e Irreversibilidade Operacional

**Status:** ACEITA  

## 1. Locks Estratégicos
O MesaFlow OS constrói sua barreira de saída (Switching Cost) através de:
* **Operational Memory:** Quanto mais o sistema opera, melhor ele prevê os gargalos específicos daquela unidade.
* **Behavioral DNA:** O staff se acostuma a ser guiado pelo sistema (Cockpits), tornando qualquer sistema "passivo" obsoleto e confuso para a equipe.
* **Trust Transparency:** O *Trust Center* cria um contrato de confiança com o cliente final que competidores baseados apenas em "links de cardápio" não possuem.

## 2. Veredito Final
MesaFlow não é um software que se compra; é uma infraestrutura na qual o negócio se apoia. Uma vez instalado, removê-lo é remover a inteligência que elimina a fila.
